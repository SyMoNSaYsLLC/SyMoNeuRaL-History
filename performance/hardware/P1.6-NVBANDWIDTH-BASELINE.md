**Why `-DCMAKE_CUDA_ARCHITECTURES=120` is legitimate here rather than a forced
variable.** The project's `CMakeLists.txt` has an explicit
`CUDA_ARCH_DEFINED_BY_USER` path that honours a user-supplied value. Its
auto-detection filters against `supported_archs`, which for CUDA ≥ 13.0 is
`75 80 86 89 90 100` — **`120` is not in that list**, so this GPU's architecture
would not have been selected by auto-detection. Passing the variable uses a
supported code path; it does not override an unsupported one.

## Physical link sanity — all three implementations agree

| Implementation | H2D % of 7.88 GB/s | D2H % of 7.88 GB/s |
|---|---|---|
| HISTORICAL CuPy | 88 % | 91 % |
| P1 CUDA Runtime | 87.9 % | 91.3 % |
| **P1.6 NVBandwidth** | **88.0 %** | **91.5 %** |

**LINK HEALTHY AT NEGOTIATED GEN3 ×8** — all three implementations land in the
same physical bandwidth neighbourhood. No regression is diagnosed from
implementation-specific deltas. **Why the platform negotiates ×8 rather than the
reported ×16 maximum remains unresolved and is outside P1.6.**

Three independent implementations landing within 0.5 percentage points of one
another is the finding. The open question is the *denominator*: `width.max` reads
16 while the link negotiates 8, so "88 % / 91 % of ceiling" is 88 % / 91 % of the
**Gen 3 ×8** ceiling, not of what the slot advertises. Nothing here establishes
whether the ×8 is a slot, riser, BIOS or board limit.
