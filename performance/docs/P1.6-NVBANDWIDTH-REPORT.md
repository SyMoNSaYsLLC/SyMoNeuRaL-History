# P1.6 — NVBandwidth forward PCIe baseline report

**2026-08-24.** NVIDIA NVBandwidth **v0.10.0** @
`82fc4e8c6afa0babb8687793678f615b3b8d793e`, pristine Release build for `sm_120`
on the production host.

**No AI model was loaded, no engine started, no source patched, and no driver,
CUDA, kernel, PCIe policy, clock, power-limit, persistence or governor setting
changed.**

**Purpose:** establish an NVIDIA-authored, reproducible forward PCIe bandwidth
reference. **This does not replace** the historical CuPy Grade-A measurements or
P1's own CUDA-runtime characterisation.

## The three implementations, and why they stay separate

| | Implementation | H2D pinned | D2H pinned |
|---|---|---|---|
| **HISTORICAL** | CuPy — Grade A | 6.94 | 7.20 |
| **P1** | SyMoNeuRaL CUDA Runtime API (`benchmarks/p1_cuda_pcie.cu`) | 6.9262 | 7.1945 |
| **P1.6** | **NVIDIA NVBandwidth v0.10.0 CE** | **6.9320** | **7.2100** |

All three agree to within a fraction of a percent. **That agreement is not
licence to call them exactly comparable.**

| Comparison | Classification |
|---|---|
| HISTORICAL CuPy vs P1.6 | **DIRECTIONAL ONLY** |
| P1 CUDA-runtime vs P1.6 | **DIRECTIONAL ONLY** |
| bidirectional CE rows | **CURRENT CHARACTERIZATION ONLY** |
| SM rows | **CURRENT CHARACTERIZATION ONLY** |

Neither cross-implementation comparison is promoted to EXACT merely because all
three use CUDA copy APIs. The differences that would have to be *proven*
equivalent — pinned-memory behaviour, timing boundaries, number of internal
copies, synchronisation points, reported statistic, buffer size — were not proven
equivalent. CuPy is absent from this host entirely, so its internals cannot be
inspected at all.

| Property | HISTORICAL CuPy | P1 CUDA-runtime | P1.6 NVBandwidth |
|---|---|---|---|
| pinned memory | CuPy internals, not inspectable | `cudaHostAlloc` | tool-internal, CE path |

| internal copies | unknown | 12 recorded iterations | `--testSamples 5` per invocation |
| synchronisation | unknown | `cudaEventSynchronize` on stop | tool-internal |
| reported statistic | unknown | mean of 12 | **median** (NVBandwidth default) |
| buffer size | 512 MB row | 512 MiB | **512 MiB** |

Buffer size is the one property that genuinely matches across all three.

**Why the architecture flag is legitimate rather than forced.** The project's
`CMakeLists.txt` carries an explicit `CUDA_ARCH_DEFINED_BY_USER` path that honours
a user-supplied value. Its auto-detection filters against `supported_archs`, which
for CUDA ≥ 13.0 is `75 80 86 89 90 100` — **`120` is not in that list**, so this
GPU's architecture would not have been selected automatically. Passing
`-DCMAKE_CUDA_ARCHITECTURES=120` uses a supported code path; it does not override
an unsupported one. Configured value confirmed in `CMakeCache.txt`.

> Under simultaneous opposite-direction CE traffic, reported H2D bandwidth was
> ~5.8 % below the P1.6 one-way H2D result and reported D2H bandwidth was
> ~10.3 % below the P1.6 one-way D2H result. **This is current characterization
> only; the mechanism was not investigated in P1.6.**

**No mechanism is claimed.** In particular this report does **not** attribute the
reduction to PCIe contention: PCIe is full-duplex, and the observed reduction
alone does not establish a cause. Attributing it would be an explanation asserted
where only an observation was earned.

### On the D2H bidirectional run

Its foreground observation was cut at a two-minute limit while the process was
still running normally. It was completed in the background with **exit code 0 and
5/5 valid runs** — not a hang, not a CUDA error, not an NVBandwidth error.
**Nothing was killed and nothing was patched.**

Bidirectional testcases run two simultaneous copies per sample, so they take
materially longer than unidirectional ones; the delay was expected behaviour.

The raw file `14-bidirectional-runs.txt` contains the D2H header **twice** — once
from the cut foreground invocation, once from the background rerun. Both are
original machine output. **All ten benchmark result rows appear exactly once**,
and the raw file was **not edited** to tidy the duplicate away. The explanation
lives in a separate file, `14-bidirectional-resolution.txt`, precisely so the raw
evidence keeps a stable hash.

## Physical link sanity

| Implementation | H2D % of 7.88 GB/s | D2H % of 7.88 GB/s |
|---|---|---|
| HISTORICAL CuPy | 88 % | 91 % |
| P1 CUDA Runtime | 87.9 % | 91.3 % |
| **P1.6 NVBandwidth** | **88.0 %** | **91.5 %** |

> **LINK HEALTHY AT NEGOTIATED GEN3 x8 — all three implementations land in the
> same physical bandwidth neighbourhood. No regression is diagnosed from
> implementation-specific deltas. Why the platform negotiates x8 rather than the
> reported x16 maximum remains unresolved and is outside P1.6.**

The open question is the **denominator**. `width.max` reads 16 while the link
negotiates 8, so "88 % / 91 % of ceiling" is a fraction of the **Gen 3 ×8**
ceiling — not of what the slot advertises. Nothing measured here establishes
whether the ×8 is a slot, riser, BIOS or board limit, and P1.6 does not attempt
to find out. It is recorded as unresolved rather than quietly folded into the
verdict.
