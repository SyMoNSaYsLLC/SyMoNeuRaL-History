| Class | Components | Risk |

| Apache-2.0 / BSD | vLLM, SGLang, TensorRT-LLM, ModelOpt, nvbandwidth, nvbench, CUTLASS, cuda-samples | **low** — no network-use clause |

| **Unresolved** | **TensorRT SDK**, **TensorRT-RTX SDK**, **NIM** | **settle before P6 selection** |

**Source availability is not a production right**, and the licence covers the code
— not the model weights it loads, which are frequently the binding constraint for
a hosted service and are a separate ledger.

## 9. Is NVBandwidth ready for P1.6?

**Yes — source-ready, not built.**

`v0.10.0` @ `82fc4e8c6afa0babb8687793678f615b3b8d793e`, Apache-2.0, clean.
Build prerequisites present: nvcc 13.3, CMake 3.31.6, ninja 1.13.0, gcc 14.2.0.

It is the purpose-built tool for the P1 gap: P1's PCIe figures came from
`benchmarks/p1_cuda_pcie.cu`, deliberately labelled **CURRENT CUDA-RUNTIME PCIE
CHARACTERIZATION** and classified DIRECTIONAL ONLY against the historical CuPy
result. **NVBandwidth will not make that comparison exact either** — it is a third
implementation. What it adds is a standard, NVIDIA-authored reference other people
can reproduce.

## 14. Did anything justify changing driver or CUDA?

### NO.

Nothing in this pass produced such evidence, and P1 already established there is
no version delta to investigate — driver 610.57.04 and CUDA 13.3 **are** the
versions the historical Grade-A figures were taken on.

What P1.5 adds *against* a change: CUDA Samples v13.3, Nsight Systems and Nsight
Compute all arrive as CUDA-13.3-versioned packages, so the profiling and
diagnostic toolchain is **already matched to the installed toolkit**. Changing
CUDA would desynchronise a working, matched set to chase a regression nobody has
demonstrated.
