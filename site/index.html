Why three cells say “not applicable” and one says “not implemented”

Most of the top half of that stack exists to coordinate many GPUs. Disaggregated serving, KV-aware routing, NCCL, NIXL and topology-aware scaling are answers to problems a single workstation does not have — and pretending otherwise would be the easiest lie on this page to tell.

NVFP4 is the interesting one. This card is Blackwell, the format is supported in silicon, and the CUDA toolkit here ships the headers. What is missing is a path through our runtime: GGML has no FP4 kernels. That is a real gap, it is ours, and it is on the list rather than quietly omitted.

Gen 3 ×8 theoretical is 7.88 GB/s. The link runs at essentially its full capability — there is no tuning fix available, only avoidance. Under sustained load the link trains to Gen 3 and stops; the idle Current : 1 reading is ASPM power saving, not the ceiling. Power draw rises from ~12 W idle to ~57 W, temperature 44 °C to 48 °C.

The 107× ratio

Resident data is read at ~752 GB/s. Data crossing the host link moves at ~7 GB/s. That is a 107× gap, and every architectural decision downstream follows from it: stage once, keep resident, and treat any host round-trip as a structural cost rather than an implementation detail.

The clearest consequence is a negative result. Multi-stream copy/compute overlap — conventionally a reliable win — measured 1.00× / 0.98× / 0.93× for 2 / 4 / 8 streams here. Transfer so dominates compute that there is nothing left to hide it behind, and additional streams only add scheduling overhead.

The single-pass reduction caps its grid at 140 co-resident blocks so every block can rendezvous at grid.sync(). That ceiling is the price of one kernel launch instead of two, not a defect. The tiled GEMM is fp32-only and therefore does not engage Blackwell's tensor cores — roughly 13× behind cuBLASLt (32,338 GFLOPS), which is the expected result for a hand-written kernel against a vendor library.

Access width dominates

16-byte float4 loads measured 341 GB/s against 45 GB/s for single-byte access — a 7.4× spread from access width alone.

Privatise every accumulation

Shared-memory privatisation beat global atomics by 89.5× on a 10 M-element histogram (1.494 ms → 0.017 ms). Contention, not arithmetic, is the cost.

Launch overhead is measurable

Graph replay cut a three-kernel pipeline from 9.65 µs to 4.10 µs per iteration. Nearly half of a small-kernel loop is CPU-side launch cost.

Block size 64, not 256

Launch-configuration sweep found 64 threads per block optimal on this part, 2.36× over the worst configuration tested. The conventional 256 default costs real throughput here.

SM partitioning is constrained

Green-context auto-split fails on 70 SMs. Splits of 56,8, 48,16 and 32,32 are all rejected by the driver. Only 8,8 was accepted — yielding 5.88× critical-kernel latency improvement.

Libraries still win at GEMM

cuBLASLt reached 32,338 GFLOPS against 4,210 for a well-written tiled kernel. Write custom kernels for what libraries do not cover, not for matrix multiply.

The 48 MB L2 trap

The same device-to-device copy reports 2,202 GB/s at 8 MB and 746 GB/s at 512 MB. The small figure measures cache, not bandwidth. Any benchmark on this part with a working set under roughly 100 MB is characterising L2 — the single easiest way to publish a number that is three times too high.

Service surfaces & residencytier residency · swap cost

Model tiers are budgeting abstractions. Not every surface can hold weights simultaneously in 15.92 GiB, so residency is planned explicitly rather than left to eviction.

Conversational surface

Routed to the resident 7B by default. Latency-critical classification degrades to the 1.5B specialist rather than paying a model swap.

Compute surface

Reduction, scan, GEMM, transpose and transform operators — each a hand-written kernel compiled at runtime. Characterised in the table above.

Image surface

Unified-memory and zero-copy staging paths. Both remain subject to the ~7 GB/s host ceiling — convenience, not free bandwidth.

Environment & buildtoolchain · hygiene parameters

The build environment is pinned and isolated. Dependency sets that contradict the base stack get their own interpreter rather than mutating a working one.

$ cmake -B build -S .
$ cmake --build build -j$(nproc)

# isolated interpreter for the engine — never the base environment
$ python3 -m venv /tmp/symoneural-venv
$ /tmp/symoneural-venv/bin/pip install -r requirements.txt

Why isolation is enforced, not advised

Two dependency sets actively damage the base environment. numba-cuda pins numpy<2.5 and will silently downgrade a clean 2.5.2 install to 2.4.6 — no error, no warning. Three further packages pin cuda-core and cuda-python versions that directly contradict the working stack.

Keeping them in separate interpreters means the environment the platform depends on never moves. Build scripts verify the package count on every run so drift is visible immediately rather than at the next failure.
